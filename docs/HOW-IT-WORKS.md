# PULSAR — چگونه کار میکند

**وضعیت:** این سند جریان کامل یک دوئل واقعی را توصیف می‌کند: چه اتفاقی می‌افتد، در کدام لایه، و چرا.

وضعیتِ رفع یافته‌ها در این سند ادعا نمی‌شود، چون عدد اینجا قابل راستی‌آزمایی نبود: نسخه‌ی قبلی یک شمارِ کل در مقدمه داشت (تعداد یافته‌های «رفع‌شده») و ممیزی ۲۰۲۶-۱۰-۲۲ خودِ همان جمله را به‌عنوان ادعای تأییدنشده ثبت کرد، چون هیچ شاهد و شمارش قابل بازتولیدی پشتش نبود. منبع حقیقت، جدولِ آیتم‌به‌آیتمِ [`docs/audit/REMEDIATION-TODO-2026-10-22.md`](audit/REMEDIATION-TODO-2026-10-22.md) است (هر آیتم با شناسه، کامیت و تست)، و اعدادِ اجرای تست در جدول README که با `scripts/test_counts.py` تولید می‌شود — هر دو با کدِ همین مخزن قابل بازتولیدند، برخلاف یک عددِ ثابت در مقدمه.

## ۱. اجزای سیستم

| لایه | فناوری | مسئولیت |
|---|---|---|
| **قرارداد** | Solidity 0.8.20 روی Polygon | نگهداری پول. تنها جایی که USDT جابهجا میشود |
| **سرور** | FastAPI / Python | داور. تصمیم میگیرد چه کسی برد. امضا میکند |
| **دیتابیس** | Firestore | وضعیت ماتچها، پروفایلها، محدودیت نرخ |
| **کلاینت** | React / TypeScript | اندازهگیری واکنش. **هرگز نتیجه را تعیین نمیکند** |
| **اوراکل** | کلید امضای سرور | امضای تسویه که قرارداد میپذیرد |

**اصل حاکم:** کلاینت زمان واکنش خودش را اندازه میگیرد و **ادعا** میکند. سرور آن را اعتبارسنجی میکند. قرارداد فقط با امضای سرور پول میدهد.

## ۲. جریان کامل یک دوئل

### مرحله ۰ — اتصال و احراز هویت

```
کلاینت → GET  /api/auth/nonce        ← سرور یک nonce میدهد
کلاینت → کیف پول: امضای پیام SIWE
کلاینت → POST /api/auth/verify       ← سرور امضا را چک میکند، توکن Bearer میدهد
```

**جزئیات مهم:**
- دامنهی SIWE از `ALLOWED_DOMAIN` میآید، **نه** از هدر `Host` کلاینت (H7). یک مهاجم نمیتواند دامنهی سرور را انتخاب کند.
- توکن ۲ ساعت اعتبار دارد. `POST /api/auth/logout` آن را باطل میکند (H22) و کلاینت هنگام disconnect کیف پول صدا میزند (H22b).

### مرحله ۱ — صف و جفتسازی

```
کلاینت → اندازهگیری RTT به سرور
کلاینت → POST /api/queue { stake, rttMs }
```

**سه گیت اینجا اعمال میشوند:**

1. **سقف پینگ (H1):** اگر RTT بالای ۴۰۰ms باشد، بازیکن **رد میشود با پیام صریح** — نه اینکه بیصدا ببازد.
2. **باند مهارت (H23):** سرور ELO هر دو بازیکن را میخواند. اگر اختلاف از باند (۱۵۰، که با زمان انتظار تا ۸۰۰ گشاد میشود) بیشتر باشد، **جفت نمیشوند**. این جلوی «انتقال پول از تازهکار به کهنهکار» را میگیرد.
3. **سبد استیک:** بازیکنان با استیک متفاوت هرگز جفت نمیشوند.

### مرحله ۲ — واریز (escrow)

```
creator → approve(escrow, stake)  → createDuel(matchId, stake)
joiner  → approve(escrow, stake)  → joinDuel(matchId)
```

**سرور مستقل تأیید میکند** (H: audit #5) — با `eth_call` فقط-خواندنی چک میکند که قرارداد واقعاً هر دو استیک را دارد و وضعیت `Active` است. کلاینت نمیتواند دروغ بگوید که واریز کرده.

**گاردها:**
- `MIN_STAKE_UNITS` از `decimals()` خودِ توکن مشتق میشود (M22) — روی توکن ۱۸-اعشاری هم درست کار میکند.
- واریز fee-on-transfer رد میشود.
- `joinDuel` بعد از پنجرهی refund رد میشود (H20).

### مرحله ۳ — سه راند (پروتکل commit → reveal → submit)

برای هر راند، هر بازیکن:

```
۱. POST /api/round/commit { intentHash }     ← قبل از دیدن هدف
۲. GET  /api/round/target                     ← هدف + proof
۳. POST /api/round/result { measuredMs, resultProof, rttMs }
```

**چرا commit اول؟** تا کلاینت نتواند proof را از قبل بسازد.

**گاردهای این مرحله:**

| گارد | چه چیزی را میگیرد |
|---|---|
| **commitment نهایی (H2)** | commit دوم با hash متفاوت رد میشود — بازیکن نمیتواند بعد از دیدن هدف، تعهدش را عوض کند |
| **salt سرور (H2)** | `result_proof` به مقداری بسته است که کلاینت نمیتواند پیشبینی کند |
| **`isTrusted`** | رویدادهای برنامهنویسیشده (script) رد میشوند |
| **کف انسانی ۱۰۵ms** | واکنش زیر کف فیزیولوژیک رد میشود |
| **اعتبارسنجی plausibility** | ادعای سریعتر از آنچه سرور مشاهده کرده، رد میشود |
| **انقضای راند** | جوابی که دیر برسد، راند را از دست میدهد |

### مرحله ۴ — تعیین برنده

```
observed = (زمان رسیدن جواب) − (زمان ارسال هدف)
compensated = observed − (کمینهی RTT بازیکن ÷ ۲)
```

**چرا جبران؟ (H1)** `observed` شامل latency شبکه است که **فقط میتواند بزرگش کند**. بدون جبران، بازیکن نزدیک سرور در تساویها میبرد.

**چرا کمینه؟** جبران ساده خودش اکسپلویت است: `rtt` بزرگتر → `compensated` کوچکتر → سریعتر به نظر رسیدن. کمینه نه با بزرگکردن قابل بازی است و نه با کوچککردن (کوچکتر = جبران کمتر = ضرر).

**راندها:** بهترین از ۳. تساوی دقیق به کسی تعلق نمیگیرد.

### مرحله ۵ — تسویه

```
سرور → settle(match) → winner + امضای اوراکل
کلاینت برنده → settleDuel(proof) روی قرارداد
قرارداد → پرداخت به برنده + کارمزد به treasury
```

**پنجرهی تسویهی انحصاری (H19):** تا `MATCH_TIMEOUT` (۳۰ دقیقه) **فقط تسویه** ممکن است. refund فقط بعد از `MATCH_TIMEOUT + REFUND_GRACE` (۴۰ دقیقه) باز میشود. **بازنده نمیتواند با رها کردن، جایزهی برنده را از بین ببرد.**

**اگر پرداخت تحویل نشود (H17):** قرارداد مبلغ را در `pendingWithdrawals` **credit** میکند (مثلاً اگر توکن گیرنده را blacklist کرده باشد). کلاینت دکمهی claim دارد (H17b).

**اگر بازیکن رها کند (H24):** غایب **کل ماتچ** را forfeit میکند، نه فقط راندهای ازدسترفته. و اگر مسابقه کامل نشود و امتیاز مساوی نباشد، **جلوتر میبرد** — چون `void` به عقبمانده سود میرساند.

### مرحله ۶ — دفتر و رتبه

```
ledger: settlements/{matchId}   ← یک ردیف، idempotent
rating: ELO هر دو بازیکن بهروز میشود
```

**گارد idempotency (H3):** نوشتن دفتر در یک **تراکنش** است. دو replica نمیتوانند هر دو «ردیفی نیست» ببینند و هر دو بنویسند.

**void هیچ رتبهای را جابهجا نمیکند** — کسی نبرد.

## ۳. جریان پول

```
بازیکن A ──stake──┐
                  ├──→ قرارداد (escrow) ──→ برنده: ۹۸٪
بازیکن B ──stake──┘                     └──→ treasury: ۲٪
```

**پول هرگز از دست سرور نمیگذرد.** سرور فقط امضا میکند که چه کسی برد.

**مسیرهای خروج:**
| سناریو | نتیجه |
|---|---|
| تسویهی عادی | برنده ۹۸٪، کارمزد ۲٪ |
| تایماوت (هیچکس بازی نکرد) | هر دو refund کامل |
| رها کردن | غایب forfeit میکند، حاضر میبرد |
| پرداخت تحویلنشدنی | credit در قرارداد، claim از UI |

## ۴. چه چیزی اثبات شده و چه چیزی نه

| مسیر | وضعیت | شاهد |
|---|---|---|
| قرارداد + پول روی EVM واقعی | ✅ | ۷۹ تست forge + ۷ تست anvil |
| سرور: کل پروتکل روی HTTP | ✅ | ۱۲۷ تست pytest + سوئیتهای legacy |
| کلاینت | ⚠️ unit-tested، هرگز end-to-end با زنجیرهی واقعی drive نشده | ۷۹ تست vitest |
| **هر سه با هم** | ❌ **هرگز تست نشده** | Playwright موکول به فاز ۱۰ |

**یعنی:** یک تست testnet، **اولین باری** خواهد بود که کلاینت مرورگر با زنجیرهی واقعی روبرو میشود. انتظار مشکلات integration داشته باشید، نه باگهای منطقی.

## ۵. چه چیزی مانده

| فاز | موضوع | چرا مهم است برای تست testnet |
|---|---|---|
| **۶** | عملیات: `/api/health` کامل، metrics، admin tooling | **تا بفهمیم چرا یک ماتچ گیر کرد** |
| ۷ | ۳۹ مورد MEDIUM | بستگی به مورد دارد |
| ۸ | LOW + دسترسپذیری + i18n | نه |
| ۹ | صداقت UI | بستگی به مورد دارد |
| **۱۰** | E2E + Load + Chaos | **تست خصمانهی عامدانه** |
| ۱۱ | دروازههای انتشار | KYC/قانونی/امنیت |

**نقشهی راه واقعی:**

```
فاز ۶  →  فاز ۷-۹  →  فاز ۱۰ (تست خصمانه)
                              ↓
                    چند روز تست testnet با بازیکن واقعی
                              ↓
                    فاز ۱۱ (دروازههای انتشار)
                              ↓
                         mainnet
```

**و یک هشدار صادقانه:** تست testnet جریان کار را میگیرد، **نه مقاومت در برابر حمله**. روی testnet هیچکس انگیزهی مالی برای تقلب ندارد. ضد-تقلب نیاز به تست عامدانه دارد که ما خودمان نقش مهاجم را بازی کنیم — کار فاز ۱۰.

## ۶. یافتهی ساختاری این پروژه

**ممیزی هر لایه را جدا مرور میکرد، پس «رفع در یک لایه، بدون مسیر از لایهی دیگر» برایش نامرئی بود.**

چهار نمونه پیدا شد:

| # | مکانیزم | لایهی گمشده |
|---|---|---|
| H17b | `withdraw()` قرارداد | کلاینت |
| H15b | `identityLockedReason` | UI |
| H22b | `/api/auth/logout` | کلاینت |
| **H1b** | سقف پینگ در engine | **HTTP + کلاینت** |

**درس مکانیکی:** هر پارامتر جدید باید از مدل HTTP → store → engine ردیابی شود. گیتی که فقط از تستهای unit قابل دسترسی است، گیت نیست.
